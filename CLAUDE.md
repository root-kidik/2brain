# 2brain — правила ведения заметок

Это личная база знаний (technical notes / second brain). Каждая заметка — конспект по конкретной технологии/теме, который должен работать как самодостаточный справочник: прочитал — понял суть и можешь применить, без необходимости лезть в другие источники.

Эталонный пример структуры и стиля — папка [broker/kafka/](broker/kafka/), начиная с [broker/kafka/README.md](broker/kafka/README.md). Перед тем как писать новую заметку или менять существующую, свериться с ним.

## Структура файлов

- Одна технология/тема = одна папка (`kafka/`, `redis/`, `postgres/`), а не один файл. Имя папки: `kebab-case`, на английском.
- Папка лежит в категории-домене, как и раньше (`broker/kafka/`, `db/postgres/`, `cache/redis/`, ...). Если подходящей категории нет — создать новую, а не сваливать всё в корень.
- Внутри папки технологии — `README.md` (общее представление, точка входа) и произвольное число файлов-аспектов (`partitions-and-replication.md`, `delivery-semantics.md`, `ecosystem.md`, ...) — каждый раскрывает один связный компонент/механизм технологии.
- Имя файла-аспекта: `kebab-case`, на английском, отражает конкретный аспект, а не дублирует название технологии.
- Аспект стоит выделять в отдельный файл, когда у него набирается достаточно материала для самостоятельного разбора (термины + механика + примеры). Одна-две строчки не тянут на отдельный файл — оставить в README или в соседнем по смыслу файле.
- Если у технологии есть штатный CLI/консольный клиент (`kafka-console-producer.sh`/`kafka-console-consumer.sh`, `yt`, `redis-cli` и т.п.) — работа с ним описывается в отдельном файле-аспекте (например `cli.md`, `console-tools.md`), а не размазывается по README и другим аспектам. В этом файле обязательно: откуда взять инструмент (пакет/установка/образ), как настроить подключение (адрес кластера, аутентификация), и рабочие примеры команд для типовых операций — по тем же правилам, что и для любого файла-аспекта (см. ниже). В README в «Быстром старте» достаточно 1-2 команд для первого знакомства, дальше — ссылка на этот файл.
- Внутри каждого файла (и README, и аспекта) — `# Название` заголовком верхнего уровня, дальше `##`-секции.

## README.md технологии — обязательные секции

README — точка входа: даёт общее представление и ведёт вглубь по ссылкам, сам не пытается вместить всё.

1. **Вводный абзац** — 1-3 предложения: что это, к какому классу решений относится, какую проблему решает. Без маркетинга и общих слов.
2. **Ключевые термины** — только базовые понятия, без которых нельзя ориентироваться в остальных файлах (например для Kafka: Cluster, Broker, Topic, Partition, Producer, Consumer, Consumer Group). Термины, специфичные для одного аспекта, определяются в файле этого аспекта, а не здесь.
3. **Разделы** — список ссылок на файлы-аспекты в папке, с одной строкой на файл: что там раскрыто. Это основная навигация по теме.
4. **Плюсы** — отдельным списком, про технологию в целом, конкретные и обоснованные (не "быстрый", а "sequential I/O + zero-copy → высокий throughput").
5. **Минусы** — отдельным списком, так же конкретно, про технологию в целом.
6. **Когда использовать / когда не стоит** — короткий практический вывод: для каких задач подходит, а где есть более простая/дешёвая альтернатива. Если для вывода нужны термины уровня паттернов использования (CDC, Event Sourcing и т.п.) — определить их в профильном файле-аспекте (например `use-cases.md`) и сослаться на него, а не разворачивать определение в README.

## Файл-аспект — обязательные секции

1. **Вводный абзац** — 1-2 предложения: какой именно аспект технологии здесь разбирается и зачем он важен.
2. **Термины** — каждый термин, относящийся к этому аспекту, отдельным пунктом списка: **Термин** — точное определение (что это, зачем нужно, как соотносится с другими терминами). Понятно человеку, который видит термин впервые, но без "воды" — по существу, 1-4 предложения на термин.
3. **Как это работает** — пошагово или в виде схемы/диаграммы, если это упрощает понимание механики (см. ниже про диаграммы).
4. **Примеры использования** — обязательно рабочий, конкретный код/команды (не псевдокод), которые можно скопировать и запустить.
5. Если у аспекта есть собственные компромиссы/особенности (не совпадающие с общими плюсами/минусами технологии в README) — можно добавить короткую секцию **Особенности/trade-offs**, не дублируя README.

## Связки нескольких технологий

Отдельная категория для заметок о том, как две (или больше) технологии, у каждой из которых уже есть своя папка, стыкуются друг с другом в одном pipeline/архитектуре (например Kafka + YTsaurus Queue). Такая заметка не переизлагает сами технологии — только то, как именно они соединяются и зачем.

- Папка лежит в категории `integrations/`, имя — kebab-case из названий связываемых технологий через дефис, в алфавитном порядке (`integrations/kafka-ytsaurus-queue/`, а не `ytsaurus-queue-kafka/`).
- Внутри — `README.md` как точка входа; файлы-аспекты заводятся по тому же правилу, что и для одиночной технологии (аспект выносится в отдельный файл, когда на него набирается достаточно материала).
- Обязательные секции README связки:
  1. **Вводный абзац** — какую задачу решает именно связка этих технологий и почему не одна из них по отдельности.
  2. **Роли** — таблица «технология → её роль в связке» (например Kafka — приём событий в реальном времени, YTsaurus Queue — долгосрочное хранение и batch/ad-hoc обработка тех же данных).
  3. **Механизмы интеграции** — конкретные технические мосты между технологиями (коннекторы, протокольная совместимость, экспорт/импорт данных) с указанием источника (официальная документация, репозиторий коннектора).
  4. **Юзкейсы** — список сценариев; для каждого: постановка задачи, почему нужна именно эта связка, а не одна из технологий в одиночку, при необходимости — пример/диаграмма.
- Термины, специфичные для одной из технологий (`offset`, `partition`, `consumer group`, `dynamic table` и т.п.), в заметке о связке не переопределяются — ссылка на файл, где термин уже определён, по общему правилу ниже. Здесь определяются только термины, специфичные именно для механизма интеграции (например конкретный коннектор или компонент-мост).
- Остальные правила репозитория (диаграммы/таблицы, стиль, актуальность) действуют как обычно.

## Общее правило по терминам (README + все аспекты вместе)

Если понятие используется в папке технологии как самостоятельная концепция — где угодно: внутри определения другого термина, в "Как это работает", в примерах, в плюсах/минусах, в "Когда использовать" — оно должно быть определено (в списке терминов подходящего файла или явной расшифровкой по месту первого упоминания), а не оставаться просто упомянутым без объяснения. Исключение — общеизвестные названия сторонних продуктов/технологий, не являющиеся частью темы (например упоминание RabbitMQ как альтернативы в заметке про Kafka). Каждый термин определяется один раз, в наиболее подходящем по смыслу файле; остальные файлы при необходимости ссылаются на него markdown-ссылкой, а не копируют определение.

Тема в целом (README + все файлы-аспекты вместе) должна быть разобрана подробно (все важные аспекты покрыты), но без воды: никаких вводных про "в современном мире технологии играют важную роль", никакого повторения одного и того же разными словами, никакой истории технологии, если она не объясняет текущее поведение.

## Таблицы, схемы, диаграммы

Если сравнение/структуру/поток данных проще показать визуально — показать:

- **Таблица** — для сравнения нескольких вариантов/режимов/настроек (например acks=0 vs 1 vs all).
- **ASCII/mermaid-диаграмма** — для архитектуры, потока данных, последовательности взаимодействий (например producer → broker → replica → consumer).
- Диаграмма — это дополнение к тексту, а не замена термину/объяснению. Каждая диаграмма должна быть подписана и понятна без чтения кода.
- Если диаграмма показывает распределение сущностей по узлам/группам (партиции по брокерам, реплики по нодам и т.п.) — перед или под диаграммой должна быть таблица явного маппинга (сущность → её местоположения), чтобы количество и распределение считывались без разбора ASCII-схемы.
- Если пример/диаграмма использует конкретные параметры (RF=2, 3 брокера и т.п.), рядом обязательно текстовое объяснение общего правила/алгоритма, который привёл именно к такому результату — а не только сам результат. Читатель не должен реверс-инжинирить логику по картинке.

## Стиль

- Пишем на русском языке, термины и команды — как есть, на английском (не переводить `offset`, `broker`, `partition` и т.п.).
- Никакой воды: без вступлений уровня "в этой статье мы разберём", без повторов, без филлерных фраз.
- Конкретика важнее общих слов: цифры, названия флагов/параметров, реальные команды.
- Если термин уже объяснён в другой заметке этого репозитория — не дублировать определение полностью, а сослаться на файл (markdown-ссылкой), при необходимости с кратким уточнением в контексте текущей темы.
- Код и команды — в блоках с указанием языка (```bash, ```python, ```sql и т.д.).

## Актуальность

- Если по ходу работы выясняется, что в заметке устаревшая или неточная информация — исправлять на месте, а не оставлять как есть "для истории".
- Новые термины/детали, всплывшие в разговоре и относящиеся к уже описанной теме, — дописывать в подходящий существующий файл-аспект (или README, если это базовое понятие), а не создавать дубли. Если материала набралось на новый самостоятельный аспект — выносить в новый файл внутри папки технологии и добавлять ссылку на него в README.
