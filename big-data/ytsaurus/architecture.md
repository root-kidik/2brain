# Архитектура хранения

Как YTsaurus физически хранит данные и организует их в единое пространство имён, и какой компонент отвечает за метаданные кластера. Базовые термины Cluster/Node — см. [README.md](README.md).

## Термины

- **Master** — реплицированная группа серверов, хранящая метаданные всего кластера: дерево Cypress и список chunk'ов с их расположением на узлах. Реплики master координируются через Hydra — внутренний консенсус-протокол на основе реплицированного журнала (решает ту же задачу, что Raft/KRaft у Kafka — см. [../../broker/kafka/kraft.md](../../broker/kafka/kraft.md) для сравнения с другой системой).
- **Cypress** — виртуальное дерево объектов кластера (аналог файловой системы): таблицы, файлы, директории и документы адресуются путями вида `//home/project/orders`. Хранится в памяти master'ов и поддерживает транзакции — можно атомарно изменить целое поддерево.
- **Chunk** — единица физического хранения данных, обычно от сотен мегабайт до нескольких гигабайт. Таблица — упорядоченная последовательность chunk'ов; каждый chunk реплицируется независимо от остальных.
- **Data node** — узел, физически хранящий chunk'и на локальных дисках и отдающий их по запросу клиента или job'а.
- **Exec node** — узел, на котором выполняются jobs вычислительных операций (см. [computation.md](computation.md)). Часто data node и exec node — одна и та же машина, чтобы job мог читать chunk с локального диска (data locality).
- **Replication factor (RF)** — сколько копий chunk'а хранится на разных data node. Для "горячих" таблиц типичное значение — 3.
- **Erasure coding** — альтернатива полной репликации: chunk делится на data-части и parity-части (схема вроде Рида-Соломона), что снижает overhead хранения (условно ~1.5x против 3x при RF=3) ценой более дорогого восстановления данных при потере узла.

## Как это работает

1. Клиент создаёт таблицу в Cypress — master регистрирует путь в дереве, физических данных ещё нет.
2. Запись в таблицу разбивает поток данных на chunk'и; master выделяет каждому chunk'у набор data node для реплик и возвращает клиенту их адреса.
3. Клиент пишет данные chunk'а параллельно на все выбранные data node; после подтверждения записи master фиксирует chunk как закоммиченный в метаданных таблицы.
4. Для чтения master отдаёт клиенту список chunk'ов таблицы и их расположение; сами данные клиент читает напрямую с data node, не проходя через master на каждый read.

### Размещение chunk'ов таблицы (3 chunk'а, RF=3, кластер из 4 data node)

| Chunk | Реплики (data node) |
|---|---|
| C0 | Node 1, Node 2, Node 3 |
| C1 | Node 2, Node 3, Node 4 |
| C2 | Node 1, Node 3, Node 4 |

RF=3 означает, что каждый chunk хранится на 3 из 4 узлов, а не на всех сразу. Master распределяет реплики так, чтобы копии одного chunk'а не совпадали (иначе потеря узла = потеря данных) и чтобы суммарная нагрузка (место на диске, число реплик) была равномерно размазана по всем data node — поэтому наборы узлов для разных chunk'ов пересекаются лишь частично.

```
                    Table: //home/project/orders (3 chunks, RF=3)

 Node 1            Node 2            Node 3            Node 4
 ┌──────────┐      ┌──────────┐      ┌──────────┐      ┌──────────┐
 │ C0       │      │ C0       │      │ C0       │      │ C1       │
 │ C2       │      │ C1       │      │ C1       │      │ C2       │
 │          │      │          │      │ C2       │      │          │
 └──────────┘      └──────────┘      └──────────┘      └──────────┘
        ▲                                                    ▲
        │            метаданные (chunk → список узлов)       │
        └──────────────────────── Master ────────────────────┘
```

## Особенности/trade-offs

- Erasure coding снижает overhead хранения, но восстановление при потере узла требует чтения и пересчёта нескольких частей вместо простого копирования реплики — дороже по CPU и сети. Поэтому его обычно применяют для "холодных", редко читаемых таблиц, а не для горячих.
- На очень больших кластерах Cypress можно шардировать между несколькими master-ячейками (multicell), чтобы метаданные не упирались в память одной группы master-серверов — это отдельная настройка, не поведение по умолчанию.

## Примеры использования

```bash
# создать таблицу с явным replication factor
yt create table //home/project/orders --attributes '{replication_factor=3}'

# записать данные построчно (JSON) в таблицу
echo '{"name": "alice", "amount": 100}
{"name": "bob", "amount": 200}' | yt write-table //home/project/orders --format json

# посмотреть, из скольких chunk'ов состоит таблица и её атрибуты хранения
yt get //home/project/orders/@chunk_count
yt get //home/project/orders/@replication_factor
```
