# Партиции и репликация

Как топик физически хранится и реплицируется по брокерам, и как это связано с параллелизмом и надёжностью записи. Базовые термины Topic/Partition/Broker/Cluster — см. [README.md](README.md).

## Термины

- **Replication Factor (RF)** — сколько копий (реплик) каждой партиции хранится на разных брокерах. RF=2 значит у партиции 2 копии — на 2 из N брокеров, а не на всех.
- **Leader / Follower** — у каждой партиции один брокер-leader (принимает все read/write для неё), остальные реплики — followers, синхронизируются с leader.
- **ISR (In-Sync Replicas)** — набор реплик, полностью синхронизированных с leader'ом. Из ISR выбирается новый leader при падении старого.
- **Segment** — партиция физически хранится как набор файлов-сегментов на диске; старые сегменты удаляются/сжимаются по retention policy.
- **Retention** — время или объём хранения данных в топике (по умолчанию 7 дней), после — удаление (или compaction).
- **Log Compaction** — альтернатива retention: хранить только последнее значение для каждого ключа (полезно для "текущего состояния", например при CDC — см. [use-cases.md](use-cases.md)).
- **Acks** — настройка producer'а, сколько реплик должны подтвердить запись (`0` — не ждать, `1` — только leader, `all`/`-1` — весь ISR).

## Как это работает

1. Producer отправляет сообщение в топик → Kafka определяет партицию (по ключу — хэш, либо round-robin).
2. Сообщение дописывается в конец лога партиции на брокере-leader, реплицируется на followers.
3. Данные лежат в топике until retention истечёт — можно перечитать историю сколько угодно раз (в отличие от классических очередей типа RabbitMQ).

### Архитектура кластера (топик с 3 партициями, RF=2, 3 брокера)

Топик `orders` состоит из 3 партиций (P0, P1, P2), у каждой — 2 реплики (RF=2: 1 leader + 1 follower), распределённые по 3 брокерам:

| Партиция | Leader | Follower |
|---|---|---|
| P0 | Broker 1 | Broker 2 |
| P1 | Broker 1 | Broker 3 |
| P2 | Broker 2 | Broker 3 |

RF=2 означает, что у каждой партиции ровно 2 копии, а не 3 — то есть партиция лежит только на 2 из 3 брокеров, третий её вообще не хранит. Kafka распределяет реплики так, чтобы: (1) реплики одной партиции никогда не оказывались на одном брокере (иначе падение узла = потеря данных партиции), и (2) роли leader/follower и число партиций были равномерно размазаны по всем брокерам, чтобы никто не был перегружен. Если бы RF был равен числу брокеров (3), каждая партиция реплицировалась бы на все брокеры сразу.

```
                     Topic: orders (partitions=3, replication-factor=2)

 Broker 1                Broker 2                Broker 3
 ┌─────────────────┐     ┌─────────────────┐     ┌─────────────────┐
 │ P0 [leader]     │     │ P0 [follower]   │     │ P1 [follower]   │
 │ P1 [leader]     │     │ P2 [leader]     │     │ P2 [follower]   │
 └─────────────────┘     └─────────────────┘     └─────────────────┘
        ▲                                                 ▲
        │ write (key → hash → partition)                  │
        │                                                 │
   Producer ───────────────────────────────────────────────

   Consumer Group "billing"
   ┌───────────┐  reads P0  ┌────────────┐
   │Consumer A │◄───────────┤            │
   ├───────────┤  reads P1  │  Group     │  каждая партиция читается
   │Consumer B │◄───────────┤ coordinator│  только одним consumer'ом
   ├───────────┤  reads P2  │            │  группы одновременно
   │Consumer C │◄───────────┘            │
   └───────────┘
```

Leader обрабатывает все чтения/записи партиции, followers только реплицируют. Если leader падает — новый leader выбирается из ISR (controller делает это через Raft/KRaft, см. [kraft.md](kraft.md)).

### Настройка acks (надёжность записи producer'а)

| `acks` | Кто должен подтвердить запись | Надёжность | Latency |
|---|---|---|---|
| `0` | никто, producer не ждёт ответа | можно потерять сообщения | минимальная |
| `1` | только leader записал в свой лог | теряется, если leader упал до репликации followers | средняя |
| `all` / `-1` | все реплики из ISR | не теряется, пока жив хотя бы 1 узел ISR | максимальная |

## Примеры использования

```bash
# создать топик с 3 партициями и репликацией 2
kafka-topics.sh --create --topic orders --partitions 3 --replication-factor 2 --bootstrap-server localhost:9092

# увеличить число партиций (нельзя уменьшить обратно)
kafka-topics.sh --alter --topic orders --partitions 6 --bootstrap-server localhost:9092

# посмотреть распределение партиций/реплик/leader'ов по брокерам
kafka-topics.sh --describe --topic orders --bootstrap-server localhost:9092
```

Producer с явным `acks=all` (Python, confluent-kafka):

```python
from confluent_kafka import Producer

p = Producer({
    "bootstrap.servers": "localhost:9092",
    "acks": "all",  # ждать подтверждения от всего ISR
})
p.produce("orders", key="user-42", value="order-created")
p.flush()
```

## Особенности/trade-offs

- Число партиций = верхняя граница параллелизма consumer'ов в одной группе (партиций 10 → максимум 10 активных consumer'ов, остальные простаивают).
- Партиции нельзя уменьшить, только увеличить (и то аккуратно — это ломает порядок по ключу, т.к. хэширование меняется).
- Больше партиций → выше throughput и параллелизм, но больше накладных расходов (файловые дескрипторы, replication traffic, дольше лидер-выборы).
